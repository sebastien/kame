# Command-Line Interface

## Purpose

The CLI exposes the native runtime without defining runtime semantics. Primary
invocation either executes an explicitly supplied program or materializes build
targets. `do run` is the explicit program-execution command; inspection and
language tools also live below the `do` namespace.

The direct-execution and unified-run contracts below are specified behavior,
not an assertion that every current backend already implements them. They
supersede the previous positional-file restriction and `do expr`/`do kash`
execution interfaces.

## Invocation

```text
kame [OPTIONS] [TARGET...]
kame [OPTIONS] INPUT... [-- ARG...]
kame do COMMAND [OPTIONS] [ARG...]
```

Initial primary options are:

```text
-f, --file FILE        append a file source (repeatable)
-c, --command TEXT     append inline source (repeatable)
-C, --directory DIR    set working directory
-j, --jobs N           maximum concurrent nodes, N > 0
-n, --dry-run          plan and render without effects or processes
--force                ignore freshness and cached-task hits
--define NAME=VALUE     override a declared value with literal text (repeatable)
--tool NAME=PATH        override an executable resolver path (repeatable)
--json                 emit machine-readable events
-h, --help             show an overview of the tool
-V, --version          show the version
```

Unknown options and missing values are CLI diagnostics. In discovered
build mode, operands following `--` are literal target names. In direct
program execution and `do run`, operands following `--` are program arguments,
not entry names or CLI options. Language-level argument binding does not
implicitly forward them as recipe shell arguments.

File and inline sources may be mixed and repeated; they are not conflicting
options in execution mode. A non-integer or nonpositive jobs value is
`OPT_VALUE_INVALID`. Inspection commands retain their single-source option
contracts and do not execute appended fragments.

## Build configuration

Resolve declared value configuration before planning: explicit `--define
NAME=VALUE` overrides `KAME_<NAME>` environment entries, which override the
authored definition (including `?=` defaults). Names are case-sensitive and
preserve their authored spelling. Repeated CLI entries use the last value.
Split at the first `=`; an empty value is an empty string, and values containing
`@(...)`, quotes, or process syntax remain literal strings. Function definitions
cannot be overridden. An unknown explicit name is `DEF_INVALID` before effects;
unrelated `KAME_` environment entries are ignored.

This option works in discovered builds, inspections, and explicit source sessions.
`do render --define` retains its template-payload contract. Plan JSON includes
provided effective overrides in an optional `configuration` object. Use `do cat
NAME` to inspect a default's value. Normal dependency-value fingerprints include
the effective override when the build consumes that definition.

## Help and Version

`-h` and `--help` print an overview of the tool to stdout and exit 0. Help takes
precedence over version and over normal execution. `kame do --help` (and a
bare `kame do`) lists the utility commands, and
`kame do COMMAND --help` prints command-specific usage.
`kame do help [COMMAND]` is equivalent.

`-V` and `--version` print `kame VERSION (BUILD_ID; BUILD_TIME; BUILD_MODE)` to stdout and exit 0.

A `-h`, `--help`, `-V`, or `--version` token after `--` is a literal target name
in build mode or a program argument in run mode. One used as the value of an
option is that option's value. None of these requests help or version.

A bare invocation (no arguments) that finds no build source prints the overview
to stdout and exits 0 instead of reporting `BUILD_NO_SOURCE`. Any explicit
argument, including `-C`, restores the `BUILD_NO_SOURCE` diagnostic.

## Source Discovery

An explicit `-f` source or a first positional operand with the case-sensitive
suffix `.km`, `.kmk`, `.kash`, or `.ksh` selects the explicit runner. Collect
file and `-c` fragments in command-line order as defined under Run. Dispatch
does not depend on whether a selected file exists: missing sources report
`FS_ERR`, not a fallback to build discovery.

With only `-c` fragments and no positional build targets, use the inline runner;
there is no implicit build-file discovery. A primary invocation that instead
begins with ordinary target operands discovers the first existing source among
`Makefile.kmk`, `make.kmk`, and `src/kmk/main.kmk`. It may also append repeated
`-c` fragments: the discovered rule source and its selected targets execute
before those fragments, in the same session. Without explicit fragments or
targets, retain the ordinary default-build behavior.

For discovered builds, positional operands remain targets regardless of suffix.
For explicit runs, recognized program suffixes select additional file fragments;
other positional operands select entries of the preceding file fragment. Use
`-f FILE` for additional files without recognized suffixes and `--entry NAME`
for targets or definitions that would otherwise be mistaken for file inputs.
Entry operands must follow their source. No implicit source is loaded by
`do run`.

Use `kame -- ./output.km` in discovered build mode, or `kame do run
./Makefile.kmk --entry ./output.km`, to request an artifact whose suffix would
otherwise select program execution. A program path after
the build-mode `--` delimiter is never dispatched as a source. Direct execution
does not add `.km`, `.kash`, or `.ksh` to implicit build-file discovery.
Target-taking inspection commands such as `do plan` and `do cat` do not perform
automatic positional source dispatch; their operands remain targets. Use `-f`
to select a source for inspection. `do run` always selects its explicit source.

Without source, the CLI prints a concise error and discovery paths, except for a
bare no-argument invocation, which prints the overview and exits 0 (see Help and
Version). It does not silently create a build file. This is `BUILD_NO_SOURCE`; an
explicitly requested source that cannot be read is `FS_ERR`.

Kame value and rule sources may use top-level `include PATH` directives. Their
paths are relative to the containing source, are read before compilation, and
merge permitted source items into the same program in depth-first declaration
order. Value sources cannot introduce rules through includes.

## Target Selection

Explicit targets run in argument order while sharing one engine. Without
targets, `default` is selected when present. When no `default` is defined, the
invocation fails with `TGT_NO_DEFAULT` and reports the available literal named
targets as a note. This selection is shared by every target-taking command: the
primary invocation and `plan`, `cat`, `inputs`, `outputs`, and `span`. A
target-less invocation never prints the target list to stdout.

This section also governs `.kmk` execution through direct invocation and
`do run`. `.km` entry selection and Kash statement execution follow Run instead.

A target named `do` is requested after `--` or with a future explicit target
option; bare `do` enters the tool namespace.

## Primary Output

Human output writes progress to stderr and recipe stdout/stderr to their
corresponding streams. Each lifecycle line identifies the target and reports
the active and completed counts; a final summary reports completed and failed
targets plus elapsed wall-clock time. Successful definition values requested as
targets are written to stdout using the canonical value display
(`005-evaluation.md`). File artifact content is not printed during normal
materialization.

`--json` emits every status, process chunk, diagnostic, and terminal event as one
JSON object per line on stdout; stderr remains unused after argument parsing.
Binary process chunks are encoded as UTF-8 text when valid and otherwise as
base64 with an explicit encoding field. Runtime failures are error events.

Every JSON object contains `schema: 1`, `type`, and a type-specific payload.
Execution events additionally expose their resource key, source span when
known, discovered dependency, effect kind, and typed target value when
applicable. These are additive schema-1 fields. Checked-in golden objects
define AST, plan, diagnostic, stream, and terminal shapes before the
corresponding command is complete.

## Commands

### Help

```text
kame do help [COMMAND]
```

Print the tool overview, the command list, or one command's usage and options.
With no COMMAND it is equivalent to `kame do --help`.

### Run

```text
kame do run [OPTIONS] INPUT... [-- ARG...]
INPUT = (FILE | -f FILE | -c TEXT | -) [ENTRY...]
```

The deprecated `do expr` spelling is a compatibility alias for
`do run --lang expr`, selecting stdin when no source is supplied. It uses the
same parser, evaluator, capability policy, async joins, and cleanup; there is no
separate expression execution path. New invocations should use `do run`.

`run` composes an ordered sequence of file and inline source fragments into one
execution session. `-f`/`--file` and `-c`/`--command` append fragments where they
occur; both are repeatable and may be interleaved with positional source files.
At least one input is required. It does not convert programs to shell text,
concatenate sources and reparse them as one language, or launch a fresh engine
for each input.

Without an explicit `--lang`, each file selects its parser independently by
suffix; inline and stdin fragments use `km`. A preceding file does not change
the default parser for `-c`. `--lang LANG` overrides subsequent fragments until
another `--lang`; it is order-sensitive, not a retroactive option. The override
changes parsing, not execution authority. The inferred file languages are:

| Suffix | Language | Execution |
| --- | --- | --- |
| `.km` | `km` | Kame value program: lazy definitions and expression statements |
| `.kmk` | `kmk` | Rule program: materialize selected targets |
| `.kash` | `kash` | Kash statements and process graphs |
| `.ksh` | `kash` | Alias for `.kash`, not KornShell or a system-shell script |

`-l` is the short alias of `--lang`, including in `do parse` and `do fmt`.
`--lang` accepts `km`, `kmk`, `kash`, and `expr`. `expr` parses exactly one Kame
expression; it is a language mode, not a separate execution command. Unknown
suffixes require an explicit language; for example, `--lang kmk -f script.mk`
explicitly treats a `.mk` file as Kame rules, not GNU Make source. `.mk` is not
an additional automatically recognized suffix. Unknown language names, missing source,
or inappropriate entry operands are usage errors (exit 2). Unknown names within
a valid program are evaluation or target-resolution failures (exit 1).
A known language unavailable on the selected backend reports `FEATURE_UNSUP`
(exit 1), rather than silently selecting another parser or a system shell.

Direct execution is shorthand for the same ordered-input form of `do run`:

```sh
kame ./publication.km publication
kame do run ./publication.km publication
kame ./Makefile.kmk check
kame do run ./Makefile.kmk check
kame ./publish.kash -- preview
kame do run ./publish.kash -- preview
kame do run -c '(uppercase "hello")'
kame do run --lang expr -c '42'
kame do run --lang kash -c 'echo hello'
kame do run ./Makefile.kmk -c '(out some-symbol)'
kame do run ./values.km ./functions.km -c '(report some-symbol)'
kame do run --allow-run -c 'name = "Ada"' ./greet.kash -c '(uppercase name)'
kame do run --lang kmk -f script.mk --lang km -c '(out some-symbol)'
```

Each shorthand/explicit pair uses identical entry selection, grants, arguments,
streams, diagnostics, exit statuses, and native/WASM semantics.

#### Parse first, then execute in order

1. Load and parse every fragment and file-backed include in input order. Each
   retains its own language, source identity, and spans; label inline fragments
   distinctly, such as `<command:1>` and `<command:2>`. Syntax cannot span two
   fragments. Includes remain valid only in file-backed fragments; an inline
   fragment cannot borrow the preceding file's include base.
2. Register the combined top-level definitions and rule declarations in one
   program scope; validate names, selected entries, and static declaration
   conflicts before beginning evaluation. Duplicate top-level names are errors,
   not last-writer-wins reassignment. Normal Kash branch-local scopes remain
   lexical and are not exported to that shared scope.
3. Execute each fragment's selected work in input order, awaiting synchronous
   completion before advancing. Named entries replace the normal work for their
   associated fragment. Value/Kash statements retain source order within a fragment;
   a rule fragment materializes its selected targets or its default.
4. Share one engine, lazy dependency nodes, argument frame, cwd, invocation
   environment, capability policy, cancellation ownership, and limit budget
   throughout the session. A later expression can refer directly to an earlier
   source's definitions without serialization or a subprocess boundary.

The shared environment is the Kame program context. Shell-local variables,
`cd`, and exports inside a recipe or child process do not mutate the parent
session; process setup keys retain their per-process meaning.

All inputs are compiled before any expression, recipe, command, or output
effect runs. A missing later file, parse failure, duplicate definition, or
invalid static entry prevents earlier fragments from executing. Host-dependent
failures discovered only during evaluation stop the remaining sequence; already
committed output/effects are not rolled back. This is compilation-before-effects,
not a transactional filesystem guarantee.

Forward references to later top-level definitions are valid: input order
sequences demanded work, not visibility or eager definition evaluation. Reaching
a dependency may demand a later definition before its fragment's statements run.
Rules from several sources form one graph; ambiguous instances retain normal
rule diagnostics. Multiple rule files declaring competing defaults must be
refactored or explicitly namespaced, not silently executed in isolated scopes.

A Kash async graph is owned by the combined session. A file/inline boundary is
not an implicit await: explicitly asynchronous work may continue while later
fragments run, and shared handles can be awaited there. Join outstanding work at
normal session completion, according to Kash's invocation ownership rules.
Failure or interruption cancels and reaps the session's owned work. An accepted
earlier fragment must not replay when a later one suspends or resumes.

#### Entries and results

- **`km` files:** Register top-level definitions lazily. With explicit `ENTRY`
  operands, request only those named definitions in operand order, sharing one
  engine; do not execute unrelated expression statements. Without entries,
  evaluate top-level expression statements in source order and return the final
  expression's value. A definitions-only fragment contributes bindings without
  immediately demanding a default: `values.km -c '(out value)'` is a valid run.
  If a value-only session otherwise has no executable work, request the combined
  `default` definition; without one, a nonempty definitions-only session reports
  `TGT_NO_DEFAULT` and lists available names. An empty session source succeeds
  without a result. A selected entry is a value, not an implicit function call.
- **`kmk` files:** `ENTRY` operands are targets. With no entries, select `default` as
  in Target Selection. Preserve file freshness, cached tasks, effects, and
  build-mode output. Top-level expressions do not become an alternate entry
  mechanism for a rule program. Declaration-only inline `kmk` fragments add
  rules but do not insert an extra implicit default-build checkpoint; explicit
  entries on those fragments do materialize the requested targets. If a
  declaration-only session contains rule fragments and no selected work, request
  the combined `default` target once after registration; this preserves inline
  rule execution through `--lang kmk -c TEXT`.
- **`kash` fragments:** Run statements in source order with the ownership and joining
  rules of `017-kash.md`. There are no named entry operands; pass arguments after
  `--`. Do not print a final `Process`/`Result` automatically. A Kash source with
  only definitions succeeds without demanding them or inventing a default.
- **`km` inline fragments:** Execute their expression statements at their place
  in the sequence, using the shared scope even after rule or Kash files. They
  can also add definitions; explicit entries select named values instead of
  their expression statements, as for value files. This is the default behavior of `-c` in every
  execution mode, independent of the preceding file suffix.
- **`expr` fragments:** Evaluate exactly one expression. Named entry
  operands are invalid. Unlike definition RHS parsing, literals such as `42`,
  `:nil`, and quoted strings retain their expression kinds.

In human `km` and `expr` execution, demanded output effects are written on their
specified streams, followed by the resulting value on stdout without an added
newline. The implicit result is the last executed value/expression statement
across the session, not one automatic result per fragment; a later failure
prevents that final success result from being emitted. Intermediate expression
values and unrequested definitions are not printed. With several explicit `km`
entries, print each selected value in entry order, using the same canonical
value display as selected definitions in build mode (`005-evaluation.md`).
Execution failure emits no fabricated success result. JSON execution uses the
schema-1 event/diagnostic model rather than mixing human result text into its
event stream.

#### Options and source paths

Run accepts directory, presentation, JSON, capability, timeout, and capture-limit
options. The first fragment's language selects the session's default grants;
later fragments inherit that policy and cannot broaden it by changing parser.
For instance, a `-c` expression following a rule file uses the rule invocation's
policy, while appending Kash to a pure value invocation requires explicit run
grants. Explicit capability options configure the whole invocation before any
fragment executes. Jobs, force, retry, recipe shell, log-limit, configured
process environment, and dry-run options apply to rule execution as specified
for builds. Kash additionally supports its process
timeout and configured-environment options. Reject options whose semantics are
not defined for any work in the composed session instead of silently ignoring
them. Invocation timeout and cancellation cover the whole sequence, not a fresh
budget for each fragment. Dry-run of a mixed rule/value session suppresses
process, write, and output effects in every fragment, not just its recipes.

Resolve a relative source filename beneath the invocation's selected working
directory (`-C`), independent of option order. Absolute filenames remain absolute.
Do not implicitly change cwd to the source's directory. Includes remain relative
to their containing source. This matches explicit build source selection (KB-2).

Apply the same selected directory to every file operand, including later inputs. Stdin (`-`) may
appear at most once; a repeated stdin operand is a usage error. Do not use
`eval` string conversion to erase a fragment's parser boundary or authored spans.

Bind `ARG...` using the normal language-level argument frame, including an empty
frame when `--` supplies no operands. Arguments containing whitespace remain
single values. For stdin source (`-`), executed processes cannot consume the
source stream; Kash's closed-stdin rule applies. Reading the selected source is
CLI source loading, not a grant for arbitrary language-level filesystem reads.

#### Replaced commands

`do run` replaces `do expr` and the previously specified `do kash`. Neither old
name remains a separate command or compatibility alias; it reports `CMD_UNKNOWN`
with migration help. Replace `kame do expr -c TEXT` with `kame do run --lang expr
-c TEXT`, and `kame do kash FILE` with `kame do run FILE`. Keep `expr` as a
parse/format language and preserve its evaluator and embedding APIs.

### Plan

```text
kame do plan [OPTIONS] [TARGET...]
```

Print selected rule, captures, declared inputs, outputs, and freshness without
evaluating body effects or running processes. With no TARGET, `default` is
selected as in Target Selection.

### Tools

```text
kame do tools [OPTIONS]
kame do tools check [OPTIONS] TARGETS...
```

The listing reports all authored tool references and their resolved paths as a
JSON array; an unavailable tool has an empty path and does not fail the listing.
`check` requires at least one target and validates only tools in those targets'
dependency plans. It may resolve read-only computed inputs but never renders or
executes a recipe. Missing tools report `TOOL_MISSING`, their authored reference,
and the dependency path, with a nonzero exit status. Unused rules are ignored.
Both backends implement `check`, including read-only computed dependency plans.
WASM inspection forwards filesystem/environment requests to the embedding host
and resumes the same input resolver after completion; it does not inspect an
empty in-memory filesystem in place of the host's filesystem. Capability and
planning-phase checks still apply, so writes and process launches are forbidden.

### Parse

```text
kame do parse --lang expr|template|rule|script|km|kmk|kash [FILE]
```

Parse input and print a stable JSON AST for tooling. Missing file reads stdin.
AST JSON includes source spans but not allocator or pointer details.
`km` validates value-program syntax; `kmk` is the rule-program spelling of the
existing `script` language. `kash` parses both `.kash` and `.ksh` source syntax.

### Format

```text
kame do fmt [--lang LANG] [--indent tabs|spaces] [--indent-width N] [-i | -n] FILE...
```

Default output is formatted source. `-i` replaces each file atomically. `-n`
prints files that would change and exits 1 when any differ. Formatting stdin is
supported only without `-i` or `-n`.
Rule bodies use tabs by default. `--indent spaces` selects spaces, with four
spaces by default; `--indent-width N` selects a width from 1 to 16. The width
option applies when spaces are selected. These options affect `rule` and
`script` formatting only.
Formatting canonicalizes whitespace within syntax and recipe indentation while
preserving the number of blank lines between script items, between recipe lines,
and at the beginning and end of script input. A blank line between a rule header
and its first recipe line is not part of the recipe and is removed. Whitespace
on otherwise blank lines is removed.

### Cat

```text
kame do cat [TARGET]
```

Materialize a target, then write exact file bytes or, for a definition value,
its canonical value display (`005-evaluation.md`) without adding a newline.
Tasks without an artifact fail with `NO_ARTIFACT`. With no TARGET, `default` is
selected as in Target Selection.

### Graph Inspection

```text
kame do inputs [--depth N] [TARGET]
kame do outputs [--depth N] [TARGET]
kame do span [--expand] [--depth N] [TARGET]
```

With no TARGET, `default` is selected as in Target Selection.

Depth zero returns no edges; one returns direct edges; `-1` is unlimited.
Outputs are stable JSON arrays. `span` separates statically known and
evaluation-dependent resources; `--expand` evaluates dynamic definitions but
does not execute recipes.

### Execution Capabilities

Value and expression execution expose `args` and `cwd`. Environment is available
only through authorized language-level access. A session whose first fragment is
`km` or `expr` denies host capabilities by default, whether invoked directly,
from a file, inline, or via stdin. Appended fragments inherit the session policy
instead of resetting or broadening it. Grant capabilities explicitly with:

```text
--allow-read[=ROOTS]
--allow-write[=ROOTS]
--allow-run[=ROOTS]
--allow-env[=NAMES]
```

`--capture-limit N` (or `--capture-limit=N`) sets the positive stdout byte
limit for each Kash command substitution. It defaults to 1 MiB, applies to
embedded substitutions in build definitions as well as `do run`, and is
independent of `--log-limit`, which governs retained recipe logs.

A scoped run grant authorizes explicit executable paths within its lexical root.
Direct argv command substitutions (`017-kash.md`) reject bare executable names
under scoped grants rather than using PATH to select a different executable.
Legacy shell-text operations require an unrestricted run grant. Run grants do
not sandbox the filesystem or environment access of the launched executable.

Standalone expression effects write before the resulting value: `out` and
`yield` write exact bytes to stdout, while `err` writes exact bytes to stderr.
`out` and `err` then return their combined output, which `do run` writes as the
expression result without adding a newline.

Sessions beginning with rules or Kash grant read and write within cwd and grant
process execution. Discovered builds count their implicit rule source as the
first fragment. The host copies the complete CLI environment into process requests,
where cached tasks fingerprint it. Language-level environment reads and access
outside cwd remain denied unless an explicit option grants them.

## Diagnostics

Human diagnostics use the structured model and information hierarchy in
`011-diagnostics.md`: outcome, authored source location, established reason,
propagation or target context, concrete recovery help, then any underlying
process cause. The source excerpt and marker use one-based locations and
tab-aware display columns. A missing source span does not invent a synthetic
location.

`--color auto|always|never` and `--diagnostic-format human|plain` are global
presentation controls specified by `011-diagnostics.md`. They do not alter
execution or JSON output. `auto` follows terminal and documented colour
environment controls; plain output remains deterministic and unstyled.

Stable codes, severities, structured context, and JSON parity are defined only
by `011-diagnostics.md`.

Suggestions are deterministic and limited to known operations, definitions, or
targets. Path-like unknown targets should suggest an explicit `./` where useful.

## Signals and Exit Status

The first `SIGINT` or `SIGTERM` cancels active roots and begins process-group
shutdown. A repeated signal may terminate immediately using the conventional
signal exit status.

Exit status is:

- 0 for successful execution, successful inspection, target listing, or a
  help or version request.
- 1 for parse, evaluation, build, cache, or `fmt -n` differences.
- 2 for CLI usage errors.
- 128 plus signal number for forced signal termination.

With multiple targets, any failed target makes the final status nonzero.

## Acceptance Tests

- Source discovery follows the documented order.
- A first positional `.km`, `.kmk`, `.kash`, or `.ksh` source dispatches to Run;
  missing selected files fail without build-discovery fallback.
- Direct execution and `do run` agree on output, grants, entries, argument
  frames, diagnostics, JSON, signals, and status on native and WASM hosts.
- Repeated `-f`/`-c` and positional files compose one program, in operand order;
  discovered-build operands, build-mode `--`, and explicit `--entry` preserve
  literal target behavior for names ending with program suffixes.
- All fragments and includes parse and register before effects. A malformed
  later fragment, missing file, duplicate name, or invalid static entry prevents
  earlier work from running; runtime failures stop subsequent work without rollback.
- Definitions, selected dependencies, args, cwd, authority, and limits are shared
  across fragments; a later `-c` can use file definitions directly. Lazy forward
  references remain valid; async handles can cross fragment boundaries and
  outstanding async work is joined at session completion.
- `-c` defaults to value-program syntax after any file language; `--lang` is an
  explicit forward-scoped override. Mixing files and commands is not a conflict.
- `km` requests only selected definitions, or runs expression statements and
  returns the final value; definitions-only defaults remain lazy.
- `.kmk` direct execution preserves target selection, freshness, and task behavior;
  `.kash`/`.ksh` execute the same Kash language, not a system shell.
- Inline and stdin run modes accept explicit languages; single-expression mode
  preserves literal kinds, exact result bytes, and argument binding.
- Unknown languages and language-inappropriate options fail before host effects.
- Relative program sources resolve beneath `-C`, without changing cwd to the
  source directory; stdin source is not consumed by launched processes.
- `do expr` and `do kash` are removed and provide deterministic migration help.
- No target selects `default`; when it is absent the invocation fails with
  `TGT_NO_DEFAULT` and reports the available targets.
- Multiple roots share one dependency execution.
- `-j 0` is rejected; `-j 1` is deterministic.
- Dry-run performs no process, write, or output effect.
- Human process output remains on its original stream.
- JSON output is valid JSON Lines and safely represents binary chunks.
- `fmt -n` and `fmt -i` have the documented atomic behavior and statuses.
- `cat` adds no newline.
- Initial value/expression sessions deny host capabilities by default; initial
  rule/Kash sessions use their normal defaults. Later fragments never implicitly
  broaden or reset the invocation policy, across direct and explicit run forms.
- `--help` and `--version` write to stdout and exit 0; help wins over version.
- A help or version token after `--`, or used as an option value, is not a
  request.
- A bare invocation without a build source prints the overview and exits 0.
- `do` with no command lists the utility commands and exits 0.
- A first termination signal cleans up process groups before exit.
- CLI usage, build failure, and signal exits use the documented statuses.

The end-to-end conformance suite that exercises these acceptance tests through
the compiled binary is specified in `013-tests.md`.

Tool overrides split at the first `=` and require a nonempty name and path. The
last occurrence wins. Paths containing `/` resolve beneath `-C` when relative;
bare values are executable names resolved against startup PATH. Overrides apply
to `(tool NAME)` and authored executable references, including unified source
sessions. They do not launch a process. Plan JSON exposes selected declarative
tool paths; changing the executable file participates in dependency identity.
